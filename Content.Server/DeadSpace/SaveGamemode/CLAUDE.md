# SaveGamemode — подсказка для работы с кодом

Режим: в конце раунда карта сохраняется в файл, в начале следующего раунда поднимается из файла
и регистрируется как станция. Всё чинится в основном на ЗАГРУЗКЕ — старые сохранения должны
работать без пересохранения.

## Файлы

- `SaveGamemodeRuleSystem.cs` — правило раунда: загрузка на `Started`, сохранение на `RoundEndedEvent`,
  регистрация станции, применение состояния. Центр всего.
- `SaveSystem.cs`, `SaveSystem.Stations.cs` — ввод-вывод: `map.yml` — карта через
  `_mapLoader.SerializeEntitiesRecursive` с фильтрами; `station.yml` — состояние станций
  (имя, `Ids` сеток по `BecomesStation`, счета, имена сеток).
  Путь: `/Saves/GameMode/<slot>/` (на сервере, НЕ в этом репозитории — здесь сейвов нет).
- `SaveGamemodeRuleComponent.cs` — настройка правила: `saveSlot` и `perMapSlot`.
  `perMapSlot: true` — слот свой для каждой карты, имя = id прототипа выбранной карты
  (`ResolveSlot`, санитайз `SanitizeSlot`): папки нет — раунд на обычной карте и в конце
  сохраняется в новую папку; папка есть — поднимается из неё. `perMapSlot: false` — общий слот
  `saveSlot`, как у пары `SaveGamemodeDeathmatch`/`SaveGamemodeExtended`.
  Конец раунда обязан брать то же имя, что и старт: `GameMapManager` после раунда уже выбирает
  СЛЕДУЮЩУЮ карту, поэтому id карты запоминается на `OnLoadingMaps` в `_roundMapId`
  (`GetSelectedMap()` — только фолбэк для запуска правил вне стандартного старта).
- `MapFilterConfig.cs` — списки фильтров для записи карты.
- `MapStateFilter.cs` — постобработка YAML: корневые списки `maps/grids/orphans/nullspace`,
  срезание компонентов с мёртвыми ссылками.
- `SaveGamemodeMobStateSystem.cs` + `SavedMobStateComponent.cs` — состояние существ (`MobState` и урон),
  которого в файле нет: перед записью на существ навешивается метка, после записи снимается, на загрузке
  состояние возвращается и метка удаляется. Сейвы без метки лечатся выводом (`InferOldSaveState`:
  пороги, `RottingComponent`) — старые файлы работают без пересохранения.
- `SaveGamemodeLoadedStateSystem.cs` — переходящие процессы на загруженной карте: снимает маркеры,
  приехавшие из файла (`LatheProducing`, `InsertingMaterialStorage`), раздаёт ключи внешнего вида,
  которые навёл бы MapInit (`MaterialStorage` → `Inserting = false`), и гасит протухший
  `PowerState.IsWorking`. Новый случай того же класса — строка в таблицу, а не новая система (ловушка 8).
- `SaveGamemodeLoadedStateSystem.Machines.cs` — второй проход той же системы, `FixLoadedMachineModes`:
  режимы машин, которых в файле нет вовсе (ловушка 9). Ускоритель частиц включается назад через
  `SwitchOn`/`SetStrength`, связи сдерживающего поля собираются заново по геометрии (поле без второй
  стороны удаляется), коллекторам радиации раздаётся ключ спрайта, обелиск суперматерии получает
  нагрузку и вид по своей стадии (`RefreshLoadedObelisk` в `SuperNecroobeliskSystem`).
- `SaveGamemodeDoNotSaveSystem.cs` + `DoNotSaveComponent.cs` — общий механизм «этого в сохранении быть
  не должно» (ловушка 10): метка навешивается перед записью и снимается сразу после, на загрузке те же
  сущности удаляются из файла, написанного до появления метки. Первый случай — эвакошаттл.

## Порядок загрузки (главный путь)

1. Карта поднимается из `map.yml` (MapInit suppressed — флаг `mapInit` в файле).
2. `TryRegisterStations`:
   - `PurgeSavedStations` — удаляет сущности станций, пришедшие в файле (см. ловушку 1);
   - `SaveGamemodeDoNotSaveSystem.PurgeLoaded` — удаляет сетку эвакошаттла и прочее, помеченное
     «не сохранять» (см. ловушку 10). ДО сбора сеток: иначе шаттл попал бы в списки станции,
     а `EmergencyShuttleSystem` на `StationPostInitEvent` добавил бы второй шаттл поверх;
   - сетки без `StationMember` собираются, главная = самая большая по тайлам → `primaryId`;
   - `FindGameMapPrototype(stationIds, primaryId)` — прототип карты берётся ПО `primaryId` (ловушка 4);
   - сетки без конфигурации станции в прототипе вынимаются из события → `AttachUnconfiguredGrids`;
   - имя из `station.yml` читается ДО `PostGameMapLoad` и передаётся в него;
   - `RaiseLocalEvent(new PostGameMapLoad(proto, mapId, grids, name))` → `StationSystem.InitializeNewStation`
     → `StationPostInitEvent` → на нём `EmergencyShuttleSystem` вешает эвакошаттл и ЦентКом;
   - `ApplyStationStates` (имена/счета по `Ids`) → `RestoreStationNames`/`AttachStationGrids` —
     фолбэки для старых сейвов без станций в файле.
3. `RestoreLoadedMobStates` — состояния существ в файле нет, и возвращать его надо ДО пробуждения NPC:
   смена `MobState` усыпляет планировщик (см. `SaveGamemodeMobStateSystem`).
   `WakeLoadedNpcs` — MapInit не приходил, NPC спят. Следом `FixLoadedUseDelays`, `FixLoadedGuns`,
   `FixLoadedItemCabinets`, `FixLoadedItemSlotLocks` — то состояние, которое навёл бы MapInit, а в файле
   его нет (см. ловушку 7), и `FixLoadedTransientStates` — обратная сторона: то, что в файле есть и на
   загрузке само себя включает (см. ловушку 8). Завершает ряд `FixLoadedMachineModes` — режимы машин,
   которых в файле не было никогда (см. ловушку 9).
4. Окно `_registeringSavedMap` подавляет спавн обязательных раундстарт-сеток при регистрации.

## Ловушки (проверено на живой проблеме с стыковкой эвака)

1. **Станция сериализуется в `map.yml`**, хотя «не часть карты»: на `RoundEndedEvent` она ещё жива
   (`StationSystem` удалит её позже, на `PreRoundLobby`), сетки пишутся со ссылкой
   `StationMember.station`, а `EntitySerializer._autoInclude` затаскивает её в файл в `nullspace`.
   Без `PurgeSavedStations` получалась вторая станция из конфигурации: шаттл/ЦентКом — на новой,
   главная сетка с игроками — на старой без шаттла →
   `Attempted to call an emergency shuttle for an uninitialized station` (EmergencyShuttleSystem.cs:279)
   и отсутствие стыковки. `DockEmergencyShuttle()` обходит ВСЕ `StationEmergencyShuttleComponent`.
2. `StationNameSetupComponent.ComponentInit` при десериализации перегенерирует случайное имя —
   поэтому имя из сохранения надо передавать в `PostGameMapLoad`, переименование после события
   запаздывает (имя уже в PDA и документах).
3. `ComponentsNeedingLiveLink` срезает компонент только если ссылка мертва — на момент сохранения
   ссылки живы, так что «вырезать станцию на записи» этим не работает; вся корректная обработка —
   на загрузке.
4. Id `Empty`: у спаскапсул `BecomesStation.Id = "Empty"`, и в `_gameMap.AllMaps()` есть чужой
   прототип карты со станцией `Empty`. Без приоритета `primaryId` станция собиралась из капсул.
5. У Box-карты (`Resources/Prototypes/Maps/box.yml`) в `stations:` только `Boxstation` — остальные
   id (капсулы и пр.) движок игнорирует, их дописываем сами.
6. Один источник правды: `map.yml` — геометрия/сущности, `station.yml` — имена и счета. Станция
   из файла для нас мусорная, её имя всё равно regenerates (см. 2).
7. **Runtime-словари, которые заполняет только MapInit, в файле пусты — и предмет молча ломается.**
   Разбор на живом примере «PhotonShotgun не берётся в две руки и не стреляет»:
   - `UseDelayComponent.Delays` срезается при записи (`MapFilterConfig`: `StripAllComponents` +
     `AddDropped("UseDelay", "delays")`), а запись «default» создаёт только `UseDelaySystem.OnMapInit`
     (`SetLength(comp.Delay, DefaultId)`). MapInit сохранённой сущности не приходит → словарь пуст →
     `TryResetDelay` отказывает не «потому что ещё идёт», а «потому что нет записи».
   - `SharedWieldableSystem.TryWield` зовёт `TryResetDelay(used, checkDelayed: true)` и на отказе молча
     возвращает false (к тому же `OnUseInHand` всегда ставит `args.Handled = true`) → ни взятия, ни попапа.
     Отсюда «сломан только один прототип»: у оружия без `UseDelay` взятие работает, а `PhotonShotgun` —
     `UseDelay: 1.2` + `GunRequiresWield`, значит и не стреляет тоже. Тем же путём отказывает `SpinCylinder`.
   - Старые файлы писали `delays` как есть: `EndTime` — абсолютное время ТОГО сервера, `CurTime` нового
     начинается с нуля → `IsDelayed` истина почти до конца раунда.
   - Тот же ряд: `GunComponent.*Modified` (считает только `RefreshModifiers` из `OnMapInit`; без него
     `FireRateModified == 0`, и `AttemptShoot` падает на `TimeSpan.FromSeconds(1f / 0f)`), залипший
     `Wieldable.Wielded` (вторая рука — виртуальная, её в файле нет; с `unwieldOnUse: false` клик по
     «уже взятому» оружию только крутит режимы), замки `ItemSlots` и `ItemCabinet` (их наводит
     `MapInit`/`LockToggledEvent`).
   - `heldPrefix`: `ItemComponent.HeldPrefix` — поле прототипа, в сохранении его нет; берём из
     `MetaData(uid).EntityPrototype`.
8. **Состояние переходящего процесса: теряется то, что нельзя терять, и сохраняется то, что нельзя
   сохранять.** Общий корень — MapInit не приходил, а внешний вид в файл не пишется вообще
   (`AppearanceComponent.AppearanceDataInit` — `readOnly`, в сейве нет НИ ОДНОГО appearance-ключа).
   Разобрано на «автолаты и протолаты после загрузки постоянно с анимацией, будто в них что-то вставляют»:
   - **голый узел маркера.** `LatheProducingComponent` не имеет ни одного `[DataField]`, но
     `EntitySerializer` пишет узел типа и без полей. На загрузке `LatheProducingSystem.ComponentStartup`
     включает станку рабочий режим, а `CurrentRecipe`/`StartTime` не сериализуются → `LatheSystem.Update`
     пропускает такого, до `FinishProducing` дело не доходит, маркер не снимается никогда.
   - **ключа внешнего вида нет, а слой в прототипе видим.** Клиентский визуализатор при отсутствии ключа
     оставляет слой таким, как он написан (`Content.Client/Materials/MaterialStorageSystem.cs:27` —
     `TryGetData` не удался → выход). Слой `inserting` в `lathe.yml` был написан без `visible: false`,
     а скрыть его мог только `SharedMaterialStorageSystem.OnMapInit`. Ориентир по правильному дефолту —
     `flatpacker.yml` и `anomaly_equipment.yml`, где `visible: false` есть.
   - **наоборот, протухший `[DataField]`:** `PowerStateComponent.IsWorking` приезжает из файла, и машина
     после загрузки тянет рабочую нагрузку вместо холостой (`AddDropped("PowerState", "isWorking")` +
     `ResetWorkingStates`).
   - Хорошая новость: `Powered` у `SharedApcPowerReceiverComponent` — `[ViewVariables]`, в файле его нет →
     на первом тике питания приходит `PowerChangedEvent`, `LatheSystem.OnPowerChanged` сам продолжает
     сохранённую очередь (`Lathe.Queue` — обычное `[DataField]`, материалы не теряются). Ничего «возобновлять»
     руками не надо.
   - Что делать с новым случаем класса: строка в таблицу `SaveGamemodeLoadedStateSystem`
     (снять маркер / раздать ключ / погасить флаг) и, если состояние писало в файл, правило в
     `MapFilterConfig` (`StripAllComponents`, `AddDropped`).
9. **Режима машины в файле нет, и на загрузке его неоткуда взять — машина «забывает», что была включена.**
   Разобрано на «ускоритель частиц, генератор сдерживающего поля и коллектор радиации не сохраняют режим;
   поле живёт независимо от генератора». Это ловушка 7 с другой стороны: там словарь пустел, потому что
   его вырезали, здесь его не вырезали — его просто никогда не писали.
   - **ускоритель частиц:** `Enabled` и `SelectedStrength` блока управления были `[ViewVariables]` → в файле
     ни того, ни другого. Починка в две части: поля стали `[DataField]` (DS14-правка компонента, нужно и
     переписывание, чтобы режим вообще начал писаться), а на загрузке машина поднимается ВЫЗОВОМ
     `SetStrength`/`SwitchOn` — присваиванием полей включение не работает: не пересчитываются нагрузка,
     вид блока и всех частей и подписка на питание. Инвариант апстрима `выключен ⇒ уровень «ожидание»`
     соблюдать, иначе UI показывает включённый ускоритель при выключенном.
   - **сдерживающее поле (главная часть бага):** `Connections` и `IsConnected` не сериализуются, а сами поля
     — сущности, дети генератора (`SetParent` в `GenerateFieldConnection`) — в файле остаются. Без словаря
     генератор поля не видит, а `RemoveConnections` — единственный их удалитель (`TurnOff` поля НЕ трогает) →
     поле нельзя выключить, разрядить или снять генератором: оно «независимо от режима». Связи собираются
     заново по геометрии: поле → генератор по родителю, направление — мировой дельта-вектор, развернутый на
     −`WorldRotation` генератора (генераторы ставят повёрнутыми, а ключ связи ЛОКАЛЬНЫЙ), бывают только
     кардинальные, партнёр — ближайший генератор на той же сетке на луче. Поле без партнёра связывается даже дальше `MaxLength` (лишняя связь ничего не ломает), а удаляется
     только когда на луче нет ни одного генератора: второй умер ещё до записи, и апстрим удалил бы поле вместе
     с ним. Удаление — необратимая ветка: сначала убедись, что партнёр действительно не находится. Поле встало не по
     стороне света — только предупреждение в лог, без удаления.
   - **не любое поле можно удалять:** в `Resources/Maps/_DeadSpace/DsTram2.yml`, `Resources/Maps/corvax_glacier.yml`
     и `projections.yml` поля написаны руками и не имеют родителя-генератора — такие пропускаем.
   - **коллектор радиации:** `Enabled` — обычный `[DataField]` и в файле есть, но режим спрайта живёт только в
     appearance-ключе → «выключенный» вид при работающем коллекторе. Компонент под `[Access]`, поэтому из
     SaveGamemode не читаем его поля (RA0002), а зовём добавленный в систему `RefreshLoadedAppearance(uid)`.
   - Правило на будущее: состояние из файла не восстанавливается «присваиванием» — ищи публичный метод
     системы-владельца (`SwitchOn`, `UpdateMachineAppearance`) и, если его нет, добавь его в ту систему
     аддитивно в маркерах `// DS14-start` / `// DS14-end`.
   - **обелиск суперматерии («вырабатывает энергию, считаясь неактивным»):** тот же класс, но с двойным
     дном. `Percents`, `StateEnum`, `SequenceStarted` и `ForceCompletion` были `[ViewVariables]` → прогресс
     активации в файл не писался, а поднятая стадией `PowerSupplier.MaxSupply` (`supplyRate`) — обычный
     `[DataField]`, и он приезжал: после загрузки обелиск стоит выключенный и кормит сеть 65/245/385 кВт
     вместо заводских 10. Починка: поля стадии стали `[DataField]` (в маркерах DS14), а
     `SuperNecroobeliskSystem.RefreshLoadedObelisk` сверяет нагрузку со стадией (заводскую берёт из
     прототипа — из живого компонента брать нельзя, там уже поднятая). СТАРЫЕ файлы: стадии в них нет,
     единственный уцелевший свидетель — `IsActive` (её из сериализуемых полей ставит только порог в 25 %),
     при поднятой нагрузке выводится стадия 25 %; обелиск без активности с поднятой нагрузкой наоборот,
     возвращается к заводским 10 кВт. Второй слой того же бага: у `SuperMatterialNecroObeliskComponent`
     визуализатора на клиенте не было ВОВСЕ → спрайт `unactive` всегда (ловушка 8: без ключа слой
     остаётся как в прототипе). Визуализатор добавлен в `Content.Client/DeadSpace/Necromorphs/Necroobelisk`.
     На загрузке НИЧЕГО не спавним (kudzu, аномалии, некроморфы — дело рук `Update` по стадии), таймеры
     не трогаем. Админ-выключенный (`IsActive=false`) при стадии ≥25 % нагрузку НЕ теряет — это поведение
     апстрима, правка на загрузке его не меняет.

10. **Сущность, созданная во время раунда, живёт на карте и уезжает в `map.yml`** — тот же класс, что и
    ловушка 1 (станция), но объект другой: эвакошаттл. `EmergencyShuttleSystem.AddEmergencyShuttle`
    создаёт сетку из `/Maps/Shuttles/emergency.yml` на `StationPostInitEvent`, а `EmergencyShuttleComponent`
    — рантаймный, значит в файл он попадает. Если раунд кончился, а шаттл остался припаркованным (не
    улетел, его не отозвали), в следующем раунде он приезжает обратно: чужая сетка в списке сеток
    станции, консоли/шлюзы, которых никто не создавал, и «шаттл, который уже прилетел».
    - **общий механизм — метка `DoNotSaveComponent`** либо тег `DoNotSave` (в этом движке тег — это
      компонент `Tag`, `tags: [DoNotSave]`; отдельного поля `Tags` у `EntityPrototype` нет): на записью
      сущность вырезает пост-процессор (`RemoveEntitiesWithComponents` + `RemovePrototypesWithComponents`
      с раскрытием в список id прототипов), на загрузке `PurgeLoaded` удаляет те же сущности по их
      собственным рантайм-компонентам и по тегу — файлы, написанные до появления метки, обязаны грузиться
      без пересохранения. Новый случай = одна строка в `StampDoNotSave` и одна в `PurgeLoaded`
      (списки обязаны совпадать).
    - **удалять причаленного нельзя руками:** `DockingSystem.OnShutdown` → `Cleanup` второй стороны берёт
      `Transform(...).GridUid!.Value` и падает, если сетку уже разобрали. Поэтому перед удалением —
      публичный `Undock` с ВЫЖИВШЕЙ стороны (он обнуляет `DockedWith` обеим), а не `Del` вперемешку.
    - `RemoveEntitiesWithoutParent` подчищает содержимое вырезанной сетки; ссылку станции на шаттл
      (`StationEmergencyShuttle.EmergencyShuttle`, `EntityUid?`) чинить нечем и незачем — станция из файла
      умирает на шаг раньше в `PurgeSavedStations`.

## Диагностика по логам сервера

- `Set up station <имя> (<uid>)` раньше строки «сохранение ... загружено» = станция пришла из файла;
  позже = её создала регистрация. Станций должна быть ровно одна на карту.
- `SaveGamemode: с файлом карты пришли сущности станций (N) — убраны до регистрации...` — purge сработал.
- `SaveGamemode: с файлом карты пришли сущности, помеченные «не сохранять» (N) — удалены до регистрации
  станции (расстыковано до удаления: M). Эвакуацию станции выдаст заново при регистрации` — purge меток
  сработал, эвакошаттл из старого файла вырезан. Строки нет = в файле помеченных не было (файл уже чистый
  или шаттл улетел до сохранения). `M` должно равняться числу причаленных сеток; удаление без расстыковки
  — прямой путь к `NullReferenceException` в `DockingSystem.Cleanup`.
- `SaveGamemode: подмена стандартной карты сохранением '<имя>'` — слот найден и файл годен; `<имя>` должно
  равняться id карты при `perMapSlot`. `сохранения '<имя>' нет ... раунд идёт на стандартной карте` —
  первый раунд на этой карте (папка появится в конце раунда), это не ошибка.
- `Discovered invalid centcomm component?` — десериализованный `StationCentcommComponent` с мёртвыми
  ссылками; вместе с purged-станциями исчезает.
- На конце раунда должно быть `Emergency shuttle ... docked with stations`, без ошибки про uninitialized.
- Структура `map.yml`: корни `maps/grids/orphans/nullspace`; станции — в `nullspace`.
- После «сохранение ... загружено» обязательны строки починки состояния:
  `задержки использования на загруженной карте: заведено N, погашено M`,
  `оружие на загруженной карте: обновлено N`, `снято залипших «взято с двух рук»: M`,
  `замков слотов предметов обновлено: N`, `шкафов предметов: закрыто/открыто ...`,
  `переходящие состояния на загруженной карте: маркеров снято N, ключей внешнего вида раздано M, машин возвращено в ожидание K`,
  `состояния существ на загруженной карте: состояний возвращено N, существ с восстановленным уроном K`,
  `разбужено NPC на загруженной карте: N`,
  `режимы машин на загруженной карте: связей поля восстановлено N, сирот полей удалено M, ускорителей включено K, коллекторов обновлено P, обелисков обновлено O, стадий выведено S`.
  `SaveGamemode: поле у ... стоит не по стороне света` — геометрия не дала кардинальное
  направление: такое поле оставлено как есть, это не сломанная сборка, а связывать не к чему.
  Строка есть, но `N` нулей при спасённом включённом ускорителе — значит `enabled` не приехал из файла:
  сейв написан до DS14-правки компонента, режима в нём нет и взять его негде (поле и коллектор чинятся для любого файла).
  `обелисков обновлено` — сколько машин получили нагрузку по своей стадии; `стадий выведено` — сколько из
  них старые файлы, где стадии в файле нет и она выведена по `IsActive` и поднятой нагрузке. При обелиске,
  который «вырабатывает, будучи неактивным», обоих нулей быть не должно: ноль = правки не дошли до сущностей.
  Нули или отсутствие строки = правки до сущностей не дошли:
  сначала проверь, что сервер запущен на свежей сборке (время `Content.Server.dll` новее исходника).
  У старых сейвов (без метки `SavedMobState`) `K` будет 0 — урона в файле нет, состояние выводится по гнили.
- На записи рядом с «карта сохранена» идёт `меток состояния существ: N` — это число существ, чьё
  состояние ушло в файл. Нули при живых NPC = метка не навесилась (см. `StampMobStates`).
- Там же `помечено «не сохранять»: N` — сколько сущностей режим вырезал из файла (эвакошаттл и всё,
  что помечено тегом `DoNotSave`). При припаркованном шаттле N >= 1; если шаттл улетел до конца раунда,
  0 — это норма. Предупреждение `меток «не сохранять» снято X, а навешано было Y` означает, что мир
  изменился между навешиванием и снятием (метка осталась в живом мире) — смотреть `SaveGamemodeDoNotSaveSystem`.

## Напутствия

- Чини на загрузке, а не на записи: исправление должно чинить уже существующие сохранения.
- Не рефактори `StationSystem` / `EmergencyShuttleSystem` / движок ради режима — правки только здесь,
  с маркерами `// DS14-start` / `// DS14-end` если трогаешь чужое.
- Прогоняй мысленно три сценария: свежий сейв / старый сейв совсем без станции в файле / сейв со
  станцией в файле (текущий случай). Фолбэки `RestoreStationNames`/`AttachStationGrids` обязаны
  продолжать работать.
- Комментарии в этой папке на русском, namespace file-scoped, стиль как в остальных файлах папки.
- Сборка: `dotnet build H:\dead-space-14\SpaceStation14.slnx --configuration DebugOpt`
  (в корне `.slnx`, не `.sln`; можно точечно `Content.Server\Content.Server.csproj`).
- Правка считается сделанной только после успешной сборки: анализатор прав доступа роняет её на ровном
  месте (RA0002 — вызов метода на поле чужого компонента, например `itemSlots.Slots.TryGetValue`; бери
  слот через `_itemSlots.TryGetSlot`). Сборка упала — `dotnet run` сервер не запустит, а запуск
  готового файла уйдёт на СТАРУЮ сборку, и будет казаться, что правка не помогла. Проверяй время
  `Content.Server.dll` и присутствие новой строки лога в `bin\Content.Server\Content.Server.dll`.
- Сейвы и логи живут на установке сервера, в этом репозитории их нет — не трать время на поиск.
